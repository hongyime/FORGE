Dependency rules

T1 is the global prerequisite. Within waves, work follows the detailed dependency matrix: T2 may overlap the domain/config foundation; T3 → T4 → T5 → T6 is ordered; APIs precede UI integration; packaging precedes deployment and release tests. At most two coding agents and one heavy build/test run on this host. Final gates F1–F4 follow all 36 verified tasks.

A task is not checked merely because its commit exists. Each task requires a verify CASE receipt via forge-xtask capturing exit code, collected/executed/passed counts, and artifact refs.

Verification receipt format

Each task runs: cargo run --locked --manifest-path native/Cargo.toml -p forge-xtask -- verify CASE --evidence .omo/evidence/rust-rewrite/task-N. The helper records command, revision, fixture hashes, duration, exit code, stdout/stderr refs, and owned-resource teardown. Unknown/unimplemented cases fail nonzero.

Common gates after every native change

cargo fmt --check · cargo clippy -D warnings · cargo test --workspace --locked (with --jobs 1 on this host). WASM/SSR feature matrices run separately; do not assume mutually exclusive feature sets compile together.

TDD requirement

Every behavior change requires a failing test first. RED output must be captured before any production code lands. Implementation writes only enough to flip RED→GREEN. Refactor only after GREEN. Regression scenarios re-run after each wave integration point.

Scope boundaries

The rewrite covers all shipped first-party runtime functionality. Optional third-party tools may keep their own runtimes behind bounded JSON-over-stdio adapters. First-party Python plugins must be ported — they cannot be relabeled as third-party exceptions.

What must be preserved

END_GOAL.md and SPEC V1–V14 · existing CLI names/options/exit semantics · API routes and machine-readable payloads · config precedence · SQLite evidence/control files · platform Postgres/Redis roles · encryption formats · audit-chain verification · monotonic IDs · report/export compatibility.

What must NOT happen

No reduced-feature executable called the completed rewrite. No empty successful handlers. No skip-based green suites. No concurrent Python/Rust writers to the same live databases. No changing audit history or deleting source/session history. No metric guarantees invented from the language choice.

Unresolved issues at baseline

Collection access violation · frontend Vitest worker startup failures · service startup failures. These remain blocking until evidenced fixed or explicitly scoped to a task. Reported slices (53 Rust / 29 agent / 102 connector tests) require re-run before treatment as verified.

Migration ledger locations

native/migration/: capabilities.json, contracts.json, tests.json, session-work.json, baseline.json, parity.json, resources.json. Statuses: pending, implemented, verified, superseded, blocked. Verified requires receipt references. Blocked is never a release pass.

03

Execution gates

Four final read-only verification gates that must all approve before a release claim is valid. Each runs independently after all 36 tasks are evidenced.

F1 · Plan Compliance Audit

Read-only reviewer compares tasks 1–36, stable capability/session IDs, and receipt revision hashes to the live tree. Pass requires zero unverified required entries; a missing receipt is a failure. Returns exact revision, verdict, and citations. Command: verify plan-compliance --evidence .omo/evidence/rust-rewrite/final-F1.

F2 · Code Quality Review

Independent reviewer audits native workspace architecture, parser limits, cancellation, audit/auth/storage compatibility, and all warning/type/test gates. Re-runs fmt/clippy/workspace tests on the final revision. Attaches evidence at .omo/evidence/rust-rewrite/final-F2. Pass requires no requirement-blocking issue.

F3 · Real Manual QA

Separate QA agent runs installed CLI, API, worker, and browser journey at desktop/mobile viewport sizes. Includes failover and rollback checks with synthetic fixtures. Evidence: screenshots, HTTP/action logs, teardown receipts at .omo/evidence/rust-rewrite/final-F3. Mock-only or screenshot-only submissions do not pass.

F4 · Scope Fidelity

Independent reviewer verifies full first-party Rust scope, external-tool boundary, no lost supported features/tests, no unrequested offensive expansion, and no erased user/session work. Checks absence of Python/React application runtime from release. Attaches exact artifact/revision hashes and verdict at .omo/evidence/rust-rewrite/final-F4.

Success criteria (all required)

  1. All 36 tasks + F1–F4 approved

    Evidence-backed completion on the final native revision; six component outcomes from the approved draft hold.

  2. Complete ledger reconciliation

    Every discovered capability/test/session entry reconciled with executable proof or evidenced supersession. Required tests cannot be waived by absent services or crashed collectors.

  3. Python/React-free runtime

    Complete supported engagement journey works using native Rust without Python/React application logic; optional external tools are explicit dependencies, never core fallbacks.

  4. Data & auth compatibility preserved

    Existing data, cryptographic envelopes, IDs, audit evidence, and authorization/reportability boundaries remain compatible. Write-fenced cutover and lossless rollback must preserve every acknowledged post-cutover write and audit event. Changed runtime artifacts require renewed release tests and soak evidence.

  5. Cross-platform test receipts

    Windows/Linux/macOS-supported paths and browser targets build; full test/chaos/mutation/24h-soak receipts exist and resource behavior stays within recorded budgets.

  6. Installed system validated

    API/web/worker and backing services healthy, synthetic work completes, TPH paused set restored, and all temporary QA resources accounted for.

  7. Commits pushed to origin/main

    Intended verified commits pushed with matching SHA. Open failures block the full-rewrite completion claim; no statement of flawless operation replaces measurable evidence.

Commit strategy

One integrator owns main; coding subagents work on disjoint files/task branches and do not push. Each task produces one or more atomic conventional commits: feat(domain): ..., test(migration): ..., etc. Larger tasks may have several independently verified commits; no monolithic rewrite commit is permitted.

A task is checked off only when its verify CASE receipt exists with the correct revision SHA — not when its commit lands.

Plans under .omo/ require explicit file-only staging; never force-add the entire directory. No secrets, ignored databases, raw customer logs, or unrelated changes may be staged.

Integrator duties

Fetch and inspect upstream before push. If main moved, stop integration, reconcile normally, and retest affected scope. Never force-push, reset unrelated work, skip hooks, or claim local work is published until the remote SHA is checked. Persist short, truthful .agents/STATE.md and append .agents/JOURNAL.md decisions after each wave.
