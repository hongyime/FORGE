# FORGE Toolkit v7.0 — Chunk 4 Integration Commentary
## Phase 3: Evasion & Payload Generation — Expanded Design Notes

---

## Overview

This document expands the integration commentary for **Phase 3 — Evasion & Payload Generation**, focusing on two third-party tool integrations: **HashBuster** (s0md3v/HashBuster) and **CyberChef**. Both are referenced in the original specification but warranted deeper architectural treatment before implementation begins. This document supersedes the stub-level notes in the v7.0 blueprint.

---

## 1. HashBuster — Evasion Context Integration

### 1.1 What HashBuster Actually Does (and What We Are Not Using)

HashBuster's primary function is hash identification and cracking via multiple online lookup services (md5hashing.net, hashkiller.co.uk, etc.). **FORGE does not use this cracking functionality.** What is architecturally relevant is the multi-source lookup pattern: HashBuster fans out a single query to N independent online services and aggregates results. This pattern is directly applicable to FORGE's pre-engagement hash reputation check requirement (FR-5F.5).

> **Critical distinction:** HashBuster is a pre-engagement utility only. Its online lookups violate the offline-by-default constraint if called during an active engagement. Enforce this at the module boundary — see §1.5 below.

---

### 1.2 Where This Fits in Phase 3

Phase 3 generates obfuscated payloads. Once a payload is generated, the operator needs to know one thing before deployment: **has this exact binary been seen before, and is it already flagged?**

This is the `generate_payload_hash` + `check_hash_reputation` pipeline, mapped to FR-5F.5 in the spec. It sits at the tail end of the `forge build` command, after `EncodingChain` has produced the final artifact.

```
forge build (Phase 3 pipeline)
        │
        ▼
ObfuscationEngine.resolve_profile()
        │
        ▼
EncodingChain.apply()  <── T01–T12 technique chain
        │
        ▼
[optional] AmsiBypassInjector.prepend()
        │
        ▼
generate_payload_hash()          <- NEW: compute MD5/SHA1/SHA256
        │
        ├──► write hash to engagement DB (always)
        │
        └──► [--check-hash flag] HashReputationChecker.query()
                    │
                    ├──► VirusTotal Lookup   (requires API key)
                    ├──► MalwareBazaar       (free, no key required)
                    └──► CIRCL HASHLOOKUP    (free, self-hostable)
                                │
                                ▼
                    Reputation report -> operator console (Rich table)
```

This pipeline is **pre-engagement only**. The `--check-hash` flag must be explicitly passed; online lookups are never triggered automatically.

### 1.3 Implementation: `generate_payload_hash`

This function is already specified in FR-5F.5. The following is the target implementation:

```python
# forge/phase3/hash_utils.py

from __future__ import annotations

import hashlib
from dataclasses import dataclass


@dataclass(frozen=True)
class PayloadHashes:
    md5:    str
    sha1:   str
    sha256: str

    def as_dict(self) -> dict[str, str]:
        return {"md5": self.md5, "sha1": self.sha1, "sha256": self.sha256}


def generate_payload_hash(payload: bytes) -> PayloadHashes:
    """
    Compute MD5, SHA-1, and SHA-256 digests of a payload byte sequence.

    MD5 and SHA-1 are included specifically for VirusTotal and legacy
    hash database compatibility — not for cryptographic assurance.
    All three hashes are stored in the engagement DB and optionally
    submitted to reputation services.

    Args:
        payload: Raw bytes of the final obfuscated artifact.

    Returns:
        PayloadHashes dataclass with all three digests as hex strings.

    OPSEC:
        Never log the payload bytes. Log only the SHA-256 digest.
        See anti-pattern table in §1.10.
    """
    return PayloadHashes(
        md5=hashlib.md5(payload, usedforsecurity=False).hexdigest(),
        sha1=hashlib.sha1(payload, usedforsecurity=False).hexdigest(),
        sha256=hashlib.sha256(payload).hexdigest(),
    )
```

> **Note on `usedforsecurity=False`:** Python 3.9+ accepts this keyword on MD5/SHA-1 to signal that these are used for identification, not cryptographic integrity. This suppresses `bandit` S324 warnings correctly and documents intent explicitly — preferable to a blanket `noqa` comment.

### 1.4 Implementation: `HashReputationChecker`

The multi-source fan-out pattern from HashBuster is reimplemented here as a native FORGE class. Do **not** import or shell out to the HashBuster binary — it adds an uncontrolled subprocess dependency and its error handling is insufficient for CI pipelines.

```python
# forge/phase3/hash_reputation.py

from __future__ import annotations

import asyncio
import logging
import os
from dataclasses import dataclass, field
from enum import Enum

import httpx

from forge.phase3.hash_utils import PayloadHashes

log = logging.getLogger(__name__)


class Verdict(str, Enum):
    CLEAN   = "CLEAN"
    FLAGGED = "FLAGGED"
    UNKNOWN = "UNKNOWN"
    ERROR   = "ERROR"


@dataclass
class SourceResult:
    source:   str
    verdict:  Verdict
    detail:   str = ""
    av_count: int = 0     # engines flagging (VT only)
    total_av: int = 0     # total engines queried (VT only)


@dataclass
class ReputationReport:
    sha256:  str
    results: list[SourceResult] = field(default_factory=list)

    @property
    def is_flagged(self) -> bool:
        return any(r.verdict == Verdict.FLAGGED for r in self.results)

    @property
    def consensus(self) -> Verdict:
        verdicts = {r.verdict for r in self.results}
        if Verdict.FLAGGED in verdicts:
            return Verdict.FLAGGED
        if Verdict.CLEAN in verdicts:
            return Verdict.CLEAN
        return Verdict.UNKNOWN


class OfflineModeError(RuntimeError):
    """Raised when a reputation check is attempted with FORGE_OFFLINE_STRICT=1."""


class HashReputationChecker:
    """
    Fans out hash reputation queries to multiple sources in parallel.

    Sources (all free-tier unless noted):
        - VirusTotal v3 API  (requires VIRUSTOTAL_API_KEY; free tier: 4 req/min)
        - MalwareBazaar      (Abuse.ch; no key required; 1 req/s recommended)
        - CIRCL HASHLOOKUP   (free; self-hostable via Docker for air-gapped ops)

    PRE-ENGAGEMENT ONLY. Always call check_hash_gate() before invoking check().
    """

    VT_URL    = "https://www.virustotal.com/api/v3/files/{sha256}"
    MB_URL    = "https://mb-api.abuse.ch/api/v1/"
    CIRCL_URL = (
        os.getenv("FORGE_CIRCL_BASE_URL", "https://hashlookup.circl.lu")
        + "/lookup/sha256/{sha256}"
    )

    def __init__(
        self, vt_api_key: str | None = None, timeout: float = 10.0
    ) -> None:
        if os.getenv("FORGE_OFFLINE_STRICT") == "1":
            raise OfflineModeError(
                "FORGE_OFFLINE_STRICT=1 is set. Hash reputation checks are "
                "disabled. Unset this variable on a network-connected host "
                "during pre-engagement preparation."
            )
        self._vt_key = vt_api_key
        self._timeout = timeout

    async def check(self, hashes: PayloadHashes) -> ReputationReport:
        """Fan out to all configured sources; return aggregated report."""
        tasks = [
            self._query_malwarebazaar(hashes.sha256),
            self._query_circl(hashes.sha256),
        ]
        if self._vt_key:
            tasks.append(self._query_virustotal(hashes.sha256))
        else:
            log.warning(
                "VIRUSTOTAL_API_KEY not set — VT check skipped. "
                "Set the env var for comprehensive coverage."
            )
        results = await asyncio.gather(*tasks, return_exceptions=True)
        return ReputationReport(
            sha256=hashes.sha256,
            results=[r for r in results if isinstance(r, SourceResult)],
        )

    # ── Source adapters ───────────────────────────────────────────────

    async def _query_virustotal(self, sha256: str) -> SourceResult:
        url = self.VT_URL.format(sha256=sha256)
        try:
            async with httpx.AsyncClient(timeout=self._timeout) as client:
                resp = await client.get(
                    url, headers={"x-apikey": self._vt_key}
                )
            if resp.status_code == 404:
                return SourceResult(
                    source="VirusTotal", verdict=Verdict.UNKNOWN,
                    detail="Hash not in VT database."
                )
            resp.raise_for_status()
            stats   = resp.json()["data"]["attributes"]["last_analysis_stats"]
            flagged = stats.get("malicious", 0) + stats.get("suspicious", 0)
            total   = sum(stats.values())
            return SourceResult(
                source="VirusTotal",
                verdict=Verdict.FLAGGED if flagged > 0 else Verdict.CLEAN,
                detail=f"{flagged}/{total} engines flagged.",
                av_count=flagged,
                total_av=total,
            )
        except Exception as exc:
            log.debug("VT query failed: %s", exc)
            return SourceResult(
                source="VirusTotal", verdict=Verdict.ERROR, detail=str(exc)
            )

    async def _query_malwarebazaar(self, sha256: str) -> SourceResult:
        try:
            async with httpx.AsyncClient(timeout=self._timeout) as client:
                resp = await client.post(
                    self.MB_URL, data={"query": "get_info", "hash": sha256}
                )
            resp.raise_for_status()
            data = resp.json()
            if data.get("query_status") == "hash_not_found":
                return SourceResult(
                    source="MalwareBazaar", verdict=Verdict.UNKNOWN,
                    detail="Not in MalwareBazaar."
                )
            tags = data.get("data", [{}])[0].get("tags", [])
            return SourceResult(
                source="MalwareBazaar",
                verdict=Verdict.FLAGGED,
                detail=f"Known malware. Tags: {', '.join(tags) or 'none'}.",
            )
        except Exception as exc:
            log.debug("MalwareBazaar query failed: %s", exc)
            return SourceResult(
                source="MalwareBazaar", verdict=Verdict.ERROR, detail=str(exc)
            )

    async def _query_circl(self, sha256: str) -> SourceResult:
        url = self.CIRCL_URL.format(sha256=sha256)
        try:
            async with httpx.AsyncClient(timeout=self._timeout) as client:
                resp = await client.get(url)
            if resp.status_code == 404:
                return SourceResult(
                    source="CIRCL HASHLOOKUP", verdict=Verdict.UNKNOWN,
                    detail="Not in CIRCL database."
                )
            resp.raise_for_status()
            data = resp.json()
            return SourceResult(
                source="CIRCL HASHLOOKUP",
                verdict=Verdict.FLAGGED,
                detail=f"Known file: {data.get('FileName', 'N/A')}.",
            )
        except Exception as exc:
            log.debug("CIRCL query failed: %s", exc)
            return SourceResult(
                source="CIRCL HASHLOOKUP", verdict=Verdict.ERROR, detail=str(exc)
            )
```

### 1.5 Pre-Engagement Gate — Critical OPSEC Control

`HashReputationChecker.check()` **must never be called during an active engagement**. Querying VirusTotal with your generated payload hash during a live operation is a direct intelligence leak — threat intel platforms monitor submission patterns, and a novel hash appearing from an external IP mid-engagement is an observable event.

Enforce this gate at the CLI layer, not inside the checker class:

```python
# forge/phase3/cli.py  (relevant excerpt)

from forge.db import get_engagement
from pathlib import Path


def check_hash_gate(engagement_id: int, db_path: Path) -> None:
    """
    Raises RuntimeError if the engagement is not in PREP or COMPLETE state.
    Must be called before any HashReputationChecker instantiation.
    """
    eng = get_engagement(db_path, engagement_id)
    if eng.status not in ("PREP", "COMPLETE"):
        raise RuntimeError(
            f"Hash reputation checks are not permitted during an active "
            f"engagement (status={eng.status!r}). Run --check-hash only "
            f"during PREP or COMPLETE phases to prevent hash submission to "
            f"third-party services during live operations."
        )
```

The `FORGE_OFFLINE_STRICT=1` environment variable provides an additional hard kill-switch for air-gapped operator hosts — the check is enforced at `HashReputationChecker.__init__` and raises `OfflineModeError` before any HTTP client is instantiated.

### 1.6 Engagement DB Schema Extension

Extend the `payloads` table to persist hash values and reputation state:

```sql
-- migrations/003_add_payload_hashes.sql

ALTER TABLE payloads ADD COLUMN hash_md5         TEXT;
ALTER TABLE payloads ADD COLUMN hash_sha1        TEXT;
ALTER TABLE payloads ADD COLUMN hash_sha256      TEXT NOT NULL DEFAULT '';
-- 0=unchecked, 1=clean, 2=flagged, 3=unknown, 4=error
ALTER TABLE payloads ADD COLUMN hash_rep_status  INTEGER NOT NULL DEFAULT 0;
ALTER TABLE payloads ADD COLUMN hash_checked_at  TEXT;   -- ISO-8601 UTC
```

`hash_rep_status` uses an integer enum rather than a boolean. The `UNKNOWN` and `ERROR` states are semantically distinct from `CLEAN` — "not found in any database" is not the same as "cleared by AV engines." Preserving this distinction is an audit completeness requirement.

### 1.8 CIRCL HASHLOOKUP — Self-Hosted Option

For engagements where even pre-engagement outbound connections are restricted, CIRCL HASHLOOKUP can be self-hosted using the official Docker image:

```bash
# Pre-engagement setup on an internet-connected staging host
docker pull circl/hashlookup-server
docker run -d -p 5000:5000 circl/hashlookup-server

# Configure FORGE to use the local instance on the operator host
export FORGE_CIRCL_BASE_URL=http://localhost:5000
```

This satisfies the offline-by-default principle for the CIRCL source. VirusTotal and MalwareBazaar remain online-only and are automatically excluded when `FORGE_OFFLINE_STRICT=1`.

### 1.10 Anti-Patterns Specific to Hash Reputation

| Anti-Pattern | Risk | Correct Approach |
|---|---|---|
| Calling `HashReputationChecker` without engagement-status gate | Payload hash leaked to VT during live engagement; observable by threat intel platforms | Enforce `check_hash_gate()` as a mandatory pre-call assertion at the CLI layer |
| Treating `UNKNOWN` as `CLEAN` in any code path | Novel hashes are expected for fresh payloads — `UNKNOWN` is desirable, not a pass | Expose `UNKNOWN` explicitly in console output and DB; never conflate with `CLEAN` |
| Submitting payload bytes to any external service | Full payload exfiltration to a third party | `HashReputationChecker` submits only the hex digest string; bytes never leave the host |
| Using `hashlib.md5()` without `usedforsecurity=False` | Bandit S324 false-positive noise in CI; misleads reviewers into thinking this is crypto | Explicitly pass `usedforsecurity=False` on Python 3.9+ to document intent |
| Storing `CLEAN` verdict without a timestamp | Stale verdicts give false assurance — a payload clean today may be flagged tomorrow | Always write `hash_checked_at`; surface verdict age alongside status in the console |
| Shelling out to the HashBuster binary | Uncontrolled subprocess; fragile error handling; Python 2 compat noise in dep tree | Reimplement the fan-out pattern natively as shown in §1.4 |
| Emitting `FLAGGED` as a warning only | Operator may proceed with a known-flagged payload under time pressure | Exit code `2` on `FLAGGED`; require explicit `--force` override with audit log entry |

## 2. CyberChef — Encoding Validation Integration

### 2.1 Role in FORGE

CyberChef is **not a runtime dependency**. Its role is offline validation and encoding cross-check during development and pre-deployment phases of Phase 3. Operators use the CyberChef web app (or the `cyberchef-node` npm package for scripted validation) to verify that FORGE's `EncodingChain` output is correctly reversible using a reference implementation.

This addresses a specific failure mode: FORGE's encoding pipeline could silently produce malformed output — for example, corrupted Base64 from incorrect UTF-16LE handling on Windows PowerShell targets — that only fails at execution time on the target. CyberChef cross-referencing catches this in the pre-engagement window.

### 2.2 Validation Pipeline

```
FORGE EncodingChain.apply(raw_payload)
        │
        ▼
encoded_artifact (string)
        │
        ├──► forge build --dry-run --output-encoding-recipe
        │         │
        │         └──► emits CyberChef Recipe JSON to stdout
        │
        └──► Operator pastes encoded artifact + recipe into CyberChef
                  │
                  └──► Verifies decoded output == original raw_payload
```

FORGE emits a CyberChef-compatible recipe JSON mirroring the `EncodingChain` steps applied in reverse (decode direction). This lets the operator validate without manually reverse-engineering the chain.

### 2.3 Recipe Emission: `to_cyberchef_recipe()`

Add a `to_cyberchef_recipe()` method to `EncodingChain`:

```python
# forge/phase3/techniques/encoding.py  (addition to EncodingChain)

_CYBERCHEF_OP_MAP: dict[str, dict] = {
    "base64":   {
        "op": "From Base64",
        "args": {"alphabet": "A-Za-z0-9+/=", "remove_non_alphabet_chars": True},
    },
    "hex":      {"op": "From Hex",  "args": {"delimiter": "Auto"}},
    "xor":      {
        "op": "XOR",
        "args": {"key": "<see payload header byte 0>", "scheme": "Standard"},
    },
    "gzip_b64": {"op": "From Base64", "args": {}},
    # gzip layer: add {"op": "Gunzip", "args": {}} after the From Base64 step
}


def to_cyberchef_recipe(self) -> list[dict]:
    """
    Emit a CyberChef-compatible recipe representing the INVERSE of the
    applied encoding chain, suitable for decoding the output artifact.

    Techniques with dynamic keys (e.g., XOR) emit a placeholder.
    The operator must substitute the actual key from the payload header.

    Returns:
        List of CyberChef operation dicts in decode execution order.
    """
    recipe = []
    for step in reversed(self._steps):
        if step in _CYBERCHEF_OP_MAP:
            recipe.append(_CYBERCHEF_OP_MAP[step])
            if step == "gzip_b64":
                recipe.append({"op": "Gunzip", "args": {}})
        else:
            recipe.append({"op": f"[MANUAL: {step}]", "args": {}})
    return recipe
```

**CLI usage:**

```bash
forge build \
  --engagement acme-001 \
  --host-id h-042 \
  --payload powershell \
  --encode base64,xor,gzip_b64 \
  --dry-run \
  --output-encoding-recipe

# Emits to stdout:
# [
#   {"op": "From Base64", "args": {...}},
#   {"op": "XOR",         "args": {"key": "<see payload header byte 0>", ...}},
#   {"op": "From Base64", "args": {}},
#   {"op": "Gunzip",      "args": {}}
# ]
```

### 2.4 `cyberchef-node` CI Validation

For automated CI cross-reference (not operator-facing), use the `cyberchef-node` npm package:

```javascript
    console.error('ENCODING VALIDATION FAILED: decoded output != original.');

```

```python
# tests/phase3/test_encoding_validation.py

import json, subprocess, shutil
import pytest
from forge.phase3.techniques.encoding import EncodingChain


@pytest.mark.skipif(
    shutil.which("cyberchef-node") is None,
    reason="cyberchef-node not installed; skipping cross-reference validation"
)
def test_base64_roundtrip_cyberchef(tmp_path):
    raw   = b"System.Net.Sockets.TCPClient"
    chain = EncodingChain().add("base64")
    encoded = chain.apply(raw.decode())
    recipe  = chain.to_cyberchef_recipe()

    enc_f    = tmp_path / "encoded.txt"
    recipe_f = tmp_path / "recipe.json"
    raw_f    = tmp_path / "raw.txt"

    enc_f.write_text(encoded)
    recipe_f.write_text(json.dumps(recipe))
    raw_f.write_bytes(raw)

    result = subprocess.run(
        ["node", "scripts/validate_encoding.js",
         str(recipe_f), str(enc_f), str(raw_f)],
        capture_output=True, text=True
    )
    assert result.returncode == 0, result.stderr
```

### 3.1 Hash Collision Check

After generating a payload, FORGE can optionally submit its SHA-256 (and legacy MD5/SHA-1) hash to multiple threat intelligence databases to determine whether the artifact has been previously catalogued by security vendors. This is a **pre-engagement only** operation — it is disabled in all other engagement states.

**Usage:**

```bash
forge build \
  --engagement <id> \
  --host-id <host> \
  --payload powershell \
  --obfuscate \
  --check-hash
```

**Flag behaviour:**

| Condition | Console Output | Operator Action |
|-----------|---------------|-----------------|
| All sources: `UNKNOWN` | ✓ No match found. Safe to deploy. | Proceed |
| Any source: `FLAGGED` | ⚠ WARNING: Hash matches known signature. Exit code 2. | Regenerate with different chain or AMSI variant |
| Any source: `ERROR` | ⓘ Source unreachable. Result inconclusive. | Retry or accept risk and override with `--force` |
| Engagement not in PREP/COMPLETE | ✗ Operation blocked. | Re-run during pre-engagement PREP phase only |
| `FORGE_OFFLINE_STRICT=1` | ✗ Offline mode active. Hash check disabled. | Run on network-connected host pre-engagement |

**Sources queried in parallel:**

| Source | API Key Required | Free Tier Limit | Self-Hostable |
|--------|-----------------|-----------------|---------------|
| VirusTotal v3 | Yes (`VIRUSTOTAL_API_KEY`) | 4 req/min, 500 req/day | No |
| MalwareBazaar | No | ~1 req/s recommended | No |
| CIRCL HASHLOOKUP | No | Unrestricted | Yes (Docker) |

**Interpreting results:**

- `CLEAN` from VirusTotal (0/N engines) is the strongest positive signal.
- `UNKNOWN` from all sources is expected and desirable for freshly generated, novel payloads.
- `FLAGGED` from any source is a hard blocker. Regenerate before deployment.
- If VirusTotal is the only source reporting `FLAGGED` and the count is low (1–2/72), consider that it may be a heuristic false positive. Re-check after re-encoding with a different chain.

### 3.2 Encoding Recipe Export (CyberChef Validation)

FORGE can emit a CyberChef-compatible decode recipe for any generated payload, enabling manual validation that the encoding chain is correctly reversible.

```bash
forge build \
  --engagement <id> \
  --payload powershell \
  --encode base64,xor \
  --dry-run \
  --output-encoding-recipe > recipe.json
```

Paste the encoded payload and `recipe.json` into [CyberChef](https://gchq.github.io/CyberChef/) and verify the decoded output matches the expected plaintext. This step is **strongly recommended** the first time any new encoding chain combination is deployed.

## 5. Summary of Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| Reimplement HashBuster fan-out natively in Python | Eliminates subprocess dependency; fits async architecture; compatible with CI pipelines |
| `UNKNOWN != CLEAN` enforced throughout all code and UI paths | Prevents false assurance; novel payloads are expected to be unseen — surface that explicitly |
| Engagement-status gate at CLI, not inside checker class | Checker class remains independently testable; gate is a policy concern, not domain logic |
| `FORGE_OFFLINE_STRICT` raises at `__init__`, not at `check()` | Fails fast before any HTTP client is constructed; no ambiguity about whether a request was attempted |
| Exit code `2` on `FLAGGED` consensus | Enables CI pipeline gating on pre-deployment hash checks; `--force` override requires explicit operator acknowledgement |
| CyberChef as dev-tooling only, never in operator wheel | Keeps production distribution lean; prevents browser automation process signatures on the operator host |
| All hashes stored in engagement DB with timestamp | Supports audit completeness requirement; enables detection of stale verdict assertions |
