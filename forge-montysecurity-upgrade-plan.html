Forge Upgrade Plan From Linper, InfraHunter, and InfraSpyder

This plan reviews the three MontySecurity repositories as technique references and maps the useful parts into Forge without adding paid dependencies or requiring new API keys by default.

Forge HEAD reviewed: 731699e Mode: plan only Default: free/local/dry-run first Secrets redacted

Source Review

linper

github.com/montysecurity/linper

Useful pattern: enumerate capability first, then optionally act. It models persistence as method plus door, has dry-run/print, cleanup, limits, custom schedule, and countermeasure docs.

Forge use: defensive persistence exposure checks, cleanup validation evidence, ATT&CK mappings, and hardening report rows. Do not port offensive persistence install behavior.

InfraHunter

github.com/montysecurity/InfraHunter

Useful pattern: broad external search is converted into URL candidates, URLScan performs visual validation, screenshots are hashed, known-benign hashes are suppressed, and alerts are optionally pushed.

Forge use: source-scored hunt plans, local artifact ingestion, deterministic visual/content suppression, and validation queues before target promotion.

InfraSpyder

github.com/montysecurity/InfraSpyder

Useful pattern: search results become HTTP/HTTPS endpoint candidates, endpoints are probed, spider logs are pattern-filtered, and matching files are downloaded into per-host folders.

Forge use: scoped open-directory artifact discovery using existing local binaries, per-host evidence folders, regex allowlists, disk caps, and feed promotion from downloaded artifacts.

User Flow

1
Artifacts land.

Forge watches or scans imports/, reports, local connector outputs, Supabase configs, CTI drops, PD exports, Burp/JUnit XML, and downloaded files.

2
Feed build merges.

forge automation feed-build --source all normalizes targets, keeps provenance, preserves prior feed entries, and writes only under --apply.

3
Priority gate decides.

Targets with two sources, owned-source proof, recurrence, fresh validation evidence, or live reachable services move ahead. One-source low-confidence items remain queued.

4
Guarded live runner acts.

If ROE, scope, Docker health, memory, cooldown, and locks pass, Forge runs bounded local scanners and monitoring without operator babysitting.

5
Evidence loops back.

New URLs, open-directory files, nuclei findings, CTI indicators, and validation proofs become graph evidence, remediation work, and new feed candidates.

6
Dashboard explains state.

The UI shows current target priority, exposure duration, recurrence, proof freshness, suppression reason, owner/SLA/ticket state, and the next allowed automation action.

Safety Boundaries

  • Do not port Linper persistence install, sudo hijack, reverse shell, stealth, or cleanup actions into Forge automation.
  • Use Linper only as a defensive coverage map for persistence indicators and hardening validation.
  • Keep Forge standalone: no new paid APIs, no required Shodan/Censys/URLScan credentials, no ProjectDiscovery Cloud key by default.
  • Live scanning must keep existing ROE, scope-manifest, memory, Docker health, cooldown, lock, and rate-limit gates.
  • All provider live sync tests must be mocked; CI must not call external APIs.
  • Downloaded artifacts must be bounded by host, byte count, file count, runtime, and allowlisted patterns.
  • Secrets and local configs remain ignored; PostPlan and committed state must not contain raw keys.

Decision Needed

Recommended approval: green-light P0 and P1 only. That gives Forge the useful patterns from these repos while staying free, standalone, deterministic, and safe. P2 should wait until you deliberately provide provider keys and per-provider ROE/rate-limit choices.
